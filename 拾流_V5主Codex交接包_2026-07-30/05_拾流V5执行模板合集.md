# 0. 使用原则

本模板合集的目的不是增加文档数量，而是让：

- 不同子版本使用一致的权威字段；
- Session 权限不因上下文变化而漂移；
- 研究、实施、验证和接受保持分离；
- 阶段结果能够被主 Session独立验收；
- 高风险问题有正式暂停和路线重新审查入口；
- 普通工作不被过度治理。

必须遵守：

```text
主 Session
= 治理、阶段验收、权威状态、版本级 Git
≠ 产品实现

子版本 Session
= 研究、设计、实现、测试、报告
≠ 正式接受自己
```

同时默认：

```yaml
active_subversion_limit: 1
active_formal_stage_or_goal_limit: 1
```

专项研究、独立 Review 或有界执行 Session 可以并行服务同一个正式 Stage，但不会成为第二个正式活跃 Goal。

关于路线文件中的 `V5_X_UPSTREAM_ADOPTION_MAP.md`：

```text
默认实现
= 03 Registry + 04 Research Log + 具体 Upstream Adoption Decision

可选版本级 Snapshot
= 从上述权威资料派生的只读视图
≠ 新的独立状态源
```

# 1. 模板选择矩阵

| 工作情形 | 默认使用的模板 | 是否必需 |
|---|---|---:|
| 启动 V5-A/B/C/D 子版本 | 子版本启动包 + Version Charter | 必需 |
| 开始一个正式阶段 | Stage / Goal Contract | 必需 |
| 开展专项外部源码研究 | 专项研究 Session Contract | 按需 |
| 复制、依赖或正式采用上游机制 | Upstream Adoption Decision | 必需 |
| 阶段实施完成并申请验收 | Implementation Report | 必需 |
| 阶段发生阻塞且无法继续 | Blocking Report | 按需 |
| 需要独立复核代码、Eval 或 Evidence | Independent Review Brief | 按需 |
| 主 Session 验收一个阶段 | Stage Acceptance Decision | 必需 |
| 完成一个子版本 | Version Final Closeout | 必需 |
| 改变长期功能目标 | Roadmap Reconsideration Memo | 必需 |
| 新 Session 接任或高权重动作前恢复 | Context Recovery Record | 按触发条件 |
| 维护当前 Program 事实 | Program Current State | 必需，主 Session创建 |
| 记录长期有效决定 | Decision Ledger Entry | 按材料性决定 |
| 记录材料性上游研究 | Research Log Event | 按材料性 Episode |

# 2. 文件命名规则

建议保持：

```text
V5_A_VERSION_CHARTER.md
V5_A_STAGE_1_CONTRACT.md
V5_A_STAGE_1_IMPLEMENTATION_REPORT.md
V5_A_STAGE_1_MAIN_ACCEPTANCE.md
V5_A_FINAL_CLOSEOUT.md
```

专项 Session：

```text
V5_A_UPSTREAM_DEERFLOW_RESEARCH_CONTRACT.md
V5_A_UPSTREAM_DEERFLOW_RESEARCH_REPORT.md

V5_A_STAGE_2_INDEPENDENT_REVIEW_BRIEF.md
V5_A_STAGE_2_INDEPENDENT_REVIEW_REPORT.md
```

阻塞：

```text
V5_A_STAGE_2_BLOCKING_REPORT.md
```

路线重新审查：

```text
V5_ROADMAP_RECONSIDERATION_<TOPIC>.md
```

不要求每个文件名都机械包含全部信息。命名重点是：

- 子版本；
- 阶段或主题；
- 文档角色；
- 能与 Implementation / Acceptance 区分。

# 22. 跨模板一致性检查

生成任何正式文件前检查：

## 22.1 权限

- 主 Session 是否被要求实施代码？
- 子版本 Session 是否在自我接受？
- 专项 Session 是否获得了超出合同的路线权限？

## 22.2 路线

- 是否保留长期功能目标？
- 是否只是优化实现方式？
- 是否需要 Roadmap Reconsideration？

## 22.3 研究

- 是否先检查 Registry 与本地状态？
- 是否固定官方 Commit？
- 下载是否被误写为采用？
- 是否记录 License？

## 22.4 Baseline

- 风险级别是否匹配？
- Git、Schema、Corpus、Provider、Split 身份是否足够？

## 22.5 证据

- 报告是否能指向真实证据？
- Failure、Invalid、Not Exercised、Unproven 是否分开？
- 是否存在机会性重跑或丢弃失败？

## 22.6 Git

- 执行 Commit 是否经过主 Session验收？
- 主 Session 是否只处理治理文件、验收、Merge、Tag 和封存？
- Merge 冲突是否触及产品逻辑？

# 23. 最小治理闭环

普通阶段的最小闭环：

```text
Version Charter
→ Stage Contract
→ 子版本 Session实施
→ Implementation Report
→ 主 Session验收
→ Current State / Ledger / Git 更新
```

外部机制进入正式实现时：

```text
Registry
→ 有界源码研究
→ Research Log
→ Adoption Decision
→ Stage Contract
→ Implementation
```

出现路线挑战时：

```text
暂停
→ Roadmap Reconsideration Memo
→ 用户决定
→ 更新或保留长期路线
```
