# 0. 文档目的

本文件规定：

1. 长期路线、Version Charter、阶段/Goal Contract 与实现之间如何分层；
2. Codex 何时可以自主下载、克隆和研究外部项目；
3. 外部资料如何记录来源、版本、License、研究深度和实际采用情况；
4. 研究结论如何转化为 Adoption Decision，而不是直接滑入实施；
5. 不同风险 Goal 应固定什么级别的 Baseline；
6. 哪些内容构成有效证据，哪些只能作为报告或线索；
7. 如何区分有效结果、质量失败、Provider Failure、Invalid Run、Not Exercised 与 Unproven；
8. 哪些条件必须暂停并将决策权交回上级 Session；
9. 如何形成最小充分的阶段验收包；
10. 如何避免 V3.5 式治理膨胀，同时保留必要的工程纪律。

```text
主 Session 不实施产品 Goal
子版本 Session 负责研究、设计、实施、测试和报告
主 Session 负责正式阶段验收和版本级权威状态
```

# 1. 核心原则

## 1.1 外部资料不是实施授权

必须长期保持：

```text
发现一个项目或论文
≠
确认它适合拾流

下载或克隆项目
≠
完成源码研究

完成源码研究
≠
批准采用

批准采用机制
≠
批准复制代码

批准复制代码
≠
批准改变当前 Goal Scope

实现完成
≠
阶段正式接受
```

任何外部项目、论文、产品或研究备忘录，默认都只是：

```yaml
default_status: reference_input
implementation_authorized: false
```

---

## 1.2 允许成熟模块复用，不要求重复造轮子

拾流允许：

- 直接依赖成熟模块；
- 通过 Adapter 接入上游；
- 局部复制并适配代码；
- 按设计模式重写；
- 复用测试思想；
- 参考产品行为和状态机；
- 拒绝不适合的上游部分。

是否复用由：

- 拾流真实问题；
- 当前 Baseline；
- 上游实际代码和维护状态；
- License；
- 集成成本；
- 可验证性；
- 长期产品边界；

共同决定。

不以“必须全部自主实现”作为工程目标，也不以“上游已经实现”作为自动接入理由。

---

## 1.3 研究、实施、验证和接受必须分离

```text
Research
回答：机制真实存在吗，怎样工作，适不适合拾流？

Implementation
回答：拾流实际改了什么？

Validation
回答：改动是否按合同运行，产品行为是否达到目标？

Acceptance
回答：项目是否正式承认该阶段结果？
```

这些职责可以由不同 Session 完成，也可以由同一子版本 Session中的不同阶段完成；但正式接受权始终属于主 Session。

---

## 1.4 报告不能创造证据

以下均不成立：

```text
报告写了 Recovery 有效
→ Recovery 实际有效

报告解释 Provider Failure
→ 质量 Case 已通过

报告补充了 Evidence
→ 原运行当时存在该 Evidence

实现了 Rollback 代码
→ Rollback 已被实际验证

子版本 Session 判断 PASS
→ 项目已经正式接受
```

报告只能引用、组织和解释真实存在的：

- 源码；
- Commit；
- Diff；
- 测试输出；
- 运行产物；
- Provider 结果；
- Trace；
- 用户可见行为；
- 人工审查记录。

---

## 1.5 治理复杂度必须与风险匹配

低风险改动不应强制使用最高级 Baseline、独立 Eval Session 和完整治理包。

高风险改动不能因为“只是作品集项目”而省略：

- 数据迁移；
- 权威边界；
- Provider 成本；
- 副作用恢复；
- Memory 污染；
- Held-out 隔离；
- Skill Promotion；
- Rollback。

---

# 2. 规划与实施层级

拾流 V5 采用：

```text
长期功能路线
→ 当前子版本 Version Charter
→ 当前阶段 / Goal Contract
→ 子版本实施
→ Implementation Report
→ 主 Session 阶段验收
→ Version Closeout
→ Program 状态更新
```

---

## 2.1 长期功能路线

文件：

```text
拾流_V5及后续版本规划_现阶段整合版.md
```

负责冻结：

- V5-A/B/C/D 的主要产品目标；
- Personal / Corpus Intelligence；
- Artifact Reuse；
- Personalized Research；
- Controlled Search Skill Improvement；
- 权威和安全边界。

不直接授权任何代码实施。

---

## 2.2 Version Charter

Version Charter 负责明确：

- 本版本用户可见增量；
- 起始 Baseline；
- 正式 Goals / Stages；
- 非目标；
- 冻结不变量；
- 允许研究的上游方向；
- Portfolio-ready；
- Version Complete；
- Pause Conditions；
- 预期验收证据。

Version Charter 可以由当前子版本 Session起草，但只有经主 Session和用户接受的版本才是权威。

---

## 2.3 阶段 / Goal Contract

Contract 负责明确一轮有界工作：

```yaml
contract:
  mission:
  baseline:
  allowed_changes:
  protected_invariants:
  authorized_upstream_research:
  authorized_runs:
  provider_budget:
  data_access:
  success_criteria:
  pause_conditions:
  required_report:
```

Contract 是实施授权边界。

长期路线或 Version Charter 中出现某项能力，不代表当前阶段已被授权实施。

---

## 2.4 实施与阶段验收

子版本 Session在 Contract 范围内：

- 研究；
- 设计；
- 修改源码；
- 添加测试；
- 运行授权 Case；
- 形成报告。

主 Session：

- 核对 Contract；
- 审查真实证据；
- 作出 `accept / partial_accept / rework / pause / reject`。

# 3. 外部资料的分类与状态

## 3.1 资料类型

```yaml
resource_type:
  - source_repository
  - official_documentation
  - research_paper
  - product
  - release_note
  - issue_or_pull_request
  - secondary_article
  - index_repository
  - local_research_memo
```

资料强度不同：

- 官方源码和测试可证明真实实现；
- 官方文档可说明公开合同，但可能滞后于源码；
- 论文可提供方法和实验，不等于适合拾流；
- 二手文章适合发现线索，不能替代原始来源；
- 索引仓库适合检索项目，不是实验结论；
- 本地备忘录是规划输入，不是上游事实。

---

## 3.2 研究状态

Program 级 Registry 应采用类似状态：

```yaml
research_status:
  - indexed
  - initial_reconnaissance
  - docs_reviewed
  - source_reviewed
  - tests_reviewed
  - spike_completed
  - adopted
  - rejected
  - superseded
```

建议含义：

### `indexed`

仅确认资源存在，尚未形成技术判断。

### `initial_reconnaissance`

已检查官方来源、主要定位、维护状态、License 和潜在版本映射。

### `docs_reviewed`

已阅读与当前问题直接相关的官方文档。

### `source_reviewed`

已检查关键源码符号和真实控制流程。

### `tests_reviewed`

已检查上游如何验证该机制，包括失败路径。

### `spike_completed`

已在隔离环境完成有限本地实验。

### `adopted`

已形成正式 Adoption Decision，并进入某个 Version / Stage Contract。

### `rejected`

已基于证据判断不采用。

### `superseded`

旧判断或旧版本已被后续研究替代。

# 4. Codex 按需获取外部项目的机制

## 4.1 自主获取授权

对于已进入当前 Version Charter、Stage / Goal Contract 或明确专项研究任务范围的外部项目，当前子版本 Session或专项研究 Session可以在认为必要时自主：

- 下载；
- 克隆；
- 更新；
- Checkout 特定 Commit / Tag；
- 阅读官方文档；
- 查看源码和测试；
- 运行有界本地测试或 Spike。

不要求为每一次正常 Clone 单独暂停请求批准。

---

## 4.2 可以自主获取的典型情况

满足任一条件且本地没有适用副本时，可以获取：

- README 或论文不足以确认真实实现；
- 需要核对状态合同、恢复语义、失败路径或权限边界；
- 需要确认某个源码符号或测试是否存在；
- 需要比较依赖、Adapter、局部复制和重写；
- 需要运行小型、低风险、已授权 Spike；
- 本地副本来源不明、Commit 不明或版本明显过旧；
- 当前 Contract 明确要求源码级研究。

---

## 4.3 获取前检查顺序

Codex 必须先检查：

1. `03_拾流V5上游项目与研究资料注册表.yaml`；
2. 当前工作区和约定的本地 Reference 目录；
3. 已有副本的官方来源；
4. 已有 Commit / Tag / Release；
5. License；
6. 当前副本是否足以回答研究问题；
7. 本轮研究是否处于已授权版本和阶段。

已有适用副本时应优先复用，避免重复创建无法区分的多个 Clone。

---

## 4.4 来源要求

优先顺序：

```text
官方源码仓库
→ 官方文档 / Release
→ 论文作者正式项目页
→ 官方 Issue / PR
→ 可信二手资料
```

不得仅依据：

- 转载；
- 不明镜像；
- 搜索摘要；
- 聚合仓库；
- 宣传文章；

复制或执行代码。

---

## 4.5 版本固定

源码级研究应尽可能记录：

```yaml
upstream_identity:
  project:
  official_url:
  release_or_commit:
  fetched_at:
  license:
  local_path:
```

如果上游持续变化：

- 不得只记录 `main`；
- 应固定具体 Commit；
- 后续重新研究时追加新 Episode；
- 不能用新版本行为回填旧研究结果。

---

## 4.6 本地存放与 Git 边界

建议将外部项目放在：

```text
references/upstreams/
```

或仓库已有等价目录。

原则：

- 与正式 `src/`、产品测试、数据库和 Artifact 分离；
- 大型上游仓库默认不提交进拾流正式 Git；
- 论文 PDF、临时数据和大型模型默认不提交；
- 可用 `.gitignore` 排除本地 Reference；
- 不为了工作区表面干净，把整个上游镜像提交到正式仓库；
- 经批准复制到正式源码的局部代码必须记录来源和修改。

具体本地路径由当前仓库约定决定，本文件不冻结目录实现。

---

## 4.7 获取和执行的安全边界

出现以下情况必须暂停：

- License 不明确或与预期冲突；
- 需要执行来源不明的安装脚本；
- 需要下载大型模型、训练数据或高成本资产；
- 需要凭据、私有数据或付费服务；
- 需要修改正式拾流数据库、索引或 Artifact；
- 需要启动具有网络写入、远程执行或不可逆副作用的工具；
- 上游依赖要求改变 Transcript Authority、Citation 或安全边界；
- 为理解局部机制必须引入完整上游 Runtime；
- 研究开始跨入未授权后续版本。

# 5. 研究深度与停止条件

## 5.1 Initial Reconnaissance

目标：

- 项目是否真实、维护、可获取；
- 官方来源和 License；
- 主要能力；
- 可能服务哪个版本；
- 是否值得后续源码研究；
- 是否值得本地 Clone。

不要求：

- 阅读完整仓库；
- 固定最终实现；
- 运行完整 Benchmark；
- 形成依赖决策。

---

## 5.2 Just-in-time Deep Research

只在具体 Version / Stage 即将使用该机制时开展。

目标：

- 固定 Commit；
- 阅读相关源码符号；
- 阅读相关测试；
- 检查失败路径；
- 检查状态和数据合同；
- 必要时运行 Spike；
- 形成 Adoption Decision。

---

## 5.3 研究停止条件

满足以下条件时应停止继续浏览并形成结论：

- 已足以回答当前研究问题；
- 已能区分采用方式；
- 已识别主要风险和拾流差异；
- 继续阅读不会改变当前 Stage Contract；
- 上游机制不适合，已具备拒绝依据；
- 需要更深研究，但应等具体 Goal 到来。

不以“完整读完仓库”为研究完成标准。

# 6. Program 级 Registry 与研究日志

## 6.1 Registry

文件：

```text
03_拾流V5上游项目与研究资料注册表.yaml
```

它保存每个资源的**当前权威状态**：

- 是否本地存在；
- 本地路径；
- Commit / Release；
- License；
- 研究深度；
- 相关版本；
- 当前判断；
- 实际使用历史；
- 下一研究触发条件。

子版本 Session可以提出更新；主 Session在阶段验收时核对并更新 Program 级当前状态。

---

## 6.2 Research Log

文件：

```text
04_拾流V5上游研究活动日志.jsonl
```

它保存**具有材料意义的研究 Episode**。

需要记录：

- 固定新 Commit；
- 阅读关键源码；
- 阅读关键测试；
- 完成 Spike；
- 修正旧判断；
- 发现 License / 维护变化；
- 形成 Adoption Decision；
- 在具体版本实际采用；
- 拒绝或淘汰机制。

不记录：

- 每个页面点击；
- 每次 grep；
- 每次打开 README；
- 无结论的普通浏览；
- 重复阅读同一内容。

---

## 6.3 Registry 与 Log 的分工

```text
Registry
= 当前怎么判断

Research Log
= 这个判断怎样形成和变化
```

旧判断被修正时：

- Registry 更新为当前状态；
- Log 追加修正 Episode；
- 不删除历史事件。

---

## 6.4 与路线文件中 `V5_X_UPSTREAM_ADOPTION_MAP.md` 的兼容关系

长期路线文件中的：

```text
V5_X_UPSTREAM_ADOPTION_MAP.md
```

表达的是“每个版本必须明确上游机制、来源、版本、License、采用方式和拾流差异”的治理要求，而不是必须永久维护另一套独立状态库。

当前治理对该要求的正式实现是：

```text
Program 级 Registry
= 外部资源的当前状态、版本相关性和使用历史

Research Log
= 判断如何形成和变化

Upstream Adoption Decision
= 某一具体机制进入正式 Stage 前的采用与实施授权

Version Charter / Stage Contract
= 当前版本或阶段允许研究、采用和实施什么
```

因此：

- 默认不再额外创建一份与 Registry 重复维护的 `V5_X_UPSTREAM_ADOPTION_MAP.md`；
- 如某个子版本材料复杂，可以生成只读的版本级 Snapshot / View，但它必须从 Registry 和已接受的 Adoption Decision 派生；
- 版本级 Snapshot 不是新的独立权威源；
- 路线文件中的 `product_reference` 在当前统一词汇中对应 `product_or_behavior_reference`；
- 当前治理新增的 `direct_dependency`、`adapter_integration`、`research_spike`、`defer` 等模式，是对原路线采用模式的兼容扩展，不改变长期功能目标。

---

## 6.5 Research Log 状态字段

Research Log 中如使用 `adoption_effect.status`，必须复用 Registry 的统一枚举：

```yaml
adoption_status:
  - candidate
  - adopted
  - conditional
  - deferred
  - rejected
  - superseded
```

优先级、用途和角色应分别写入：

```yaml
priority:
role:
qualifier:
target_version:
recommended_modes:
```

不得将 `P0 candidate`、`candidate_as_taxonomy`、`adopted_as_research_input` 等复合描述塞入 `status` 字段。

# 7. Adoption Decision

源码研究结束后，必须形成明确判断。

```yaml
adoption_decision:
  mechanism:
  upstream_project:
  upstream_release_or_commit:
  inspected_artifacts:
  verified_behavior:
  relevant_tests:
  license:

  decision:
    - direct_dependency
    - adapter_integration
    - copy_and_adapt
    - reimplement_pattern
    - product_or_behavior_reference
    - test_reference
    - research_spike
    - defer
    - reject

  shiliu_problem:
  shiliu_specific_delta:
  copied_or_referenced_symbols:
  rejected_parts:
  implementation_cost:
  risks:
  tests_required:
  unresolved_questions:
  implementation_authorized:
```

默认：

```yaml
implementation_authorized: false
```

只有进入已接受的 Stage / Goal Contract 后，才可改为 `true`。

# 8. 各类采用方式的要求

## 8.1 `direct_dependency`

适用于：

- 上游边界稳定；
- License 兼容；
- 依赖规模合理；
- 能通过 Adapter 隔离；
- 不破坏拾流权威合同。

必须记录版本锁定和升级策略。

---

## 8.2 `adapter_integration`

保留上游主要实现，通过拾流 Adapter 映射：

- State；
- Tool；
- Storage；
- Error；
- Trace；
- UI。

应有边界测试，避免上游语义泄漏成拾流权威。

---

## 8.3 `copy_and_adapt`

必须记录：

- 上游 Commit；
- 原文件；
- 原符号；
- 复制范围；
- 本地修改；
- License / Notice；
- 为什么不直接依赖；
- 对应测试。

不得将复制代码描述为完全自主原创。

---

## 8.4 `reimplement_pattern`

可以借鉴：

- 状态机；
- 合同；
- 测试结构；
- 失败语义；
- UI 流程。

仍应记录来源和拾流差异，避免未来重复研究。

---

## 8.5 `product_or_behavior_reference`

只参考：

- 产品入口；
- 用户流程；
- 可观察状态；
- 交互设计；
- 报告形式。

不暗示代码或架构相同。

---

## 8.6 `research_spike`

Spike 必须：

- 有明确问题；
- 有时间和范围边界；
- 使用隔离数据；
- 不修改正式 Baseline；
- 结果可接受或可丢弃；
- 不因 Spike 成功自动授权正式接入。

---

# 9. Baseline 风险分级

Baseline 用于归因，不是仪式。

## 9.1 Level 0：文档和低风险治理改动

适用于：

- 文档；
- Registry；
- Research Log；
- 模板；
- 不触及产品行为的轻量 UI 文案。

最低记录：

```yaml
baseline:
  code_commit:
  branch:
  target_files:
```

---

## 9.2 Level 1：普通代码 Goal

适用于：

- 局部 Validator；
- 低风险 UI；
- 已有模块内接线；
- 无正式数据迁移的功能。

至少固定：

```yaml
baseline:
  code_commit:
  branch:
  working_tree_clean:
  relevant_tests:
  target_paths:
```

---

## 9.3 Level 2：Runtime / Memory / Schema Goal

适用于：

- ResearchTask Runtime；
- Checkpoint / Resume；
- Side Effect；
- 数据库 Migration；
- Artifact / Memory；
- User / Corpus Model；
- 复杂 Prompt / DecisionView；
- Source Version 相关变更。

至少固定：

```yaml
baseline:
  code_commit:
  branch:
  working_tree_clean:
  db_schema_version:
  corpus_snapshot:
  index_version:
  source_version_set:
  prompt_versions:
  provider_configuration:
  artifact_or_memory_version:
  migration_plan:
  rollback_plan:
```

---

## 9.4 Level 3：Eval / Skill Promotion / Held-out Goal

适用于：

- Candidate Skill；
- Promotion / Rollback；
- Replay；
- Related / Unrelated Task；
- Frozen / Held-out；
- 正式 Provider 对照；
- Judge 或 Experiment Identity。

至少固定：

```yaml
baseline:
  code_commit:
  scaffold_fingerprint:
  corpus_snapshot:
  dataset_id:
  split_hash:
  evaluator_version:
  judge_version:
  provider_configuration:
  active_skill_repo_version:
  candidate_version:
  experiment_manifest:
  access_policy:
```

---

## 9.5 Baseline 现场核验

任何文档中的旧 Commit 都不能替代当前现场核验。

执行 Session开始时应检查：

- Branch；
- HEAD；
- Working Tree；
- 未跟踪文件；
- 数据库和索引；
- 本地上游版本；
- Provider 配置；
- 当前 Contract。

发现不一致时：

- 记录差异；
- 不自行猜测；
- 必要时暂停；
- 由上级 Session决定新 Baseline。

---

# 10. Scope 与实施授权

## 10.1 Allowed Changes

Contract 应明确：

```yaml
allowed_changes:
  source_paths:
  tests:
  schema:
  migrations:
  prompts:
  ui:
  dependencies:
  reference_materials:
```

未列入的跨模块修改，默认不授权。

---

## 10.2 Protected Invariants

至少根据当前版本选择：

- Transcript / ASR 事实权威；
- Stable Citation；
- Source Version；
- Fast / Deep 既有产品路径；
- DecisionView 与完整 Runtime State 分离；
- 用户确认边界；
- Candidate 不能修改 Verifier；
- Eval Split；
- Provider Accounting；
- Tool Permission；
- Artifact / Memory Lineage。

触及受保护不变量必须暂停，除非 Contract 明确授权。

---

## 10.3 跨版本基础铺设

可以有限前置：

- Event 字段；
- Trace Identity；
- Version 字段；
- 扩展点；
- 兼容 Migration；
- 后续接口占位。

但必须：

- 服务当前 Goal；
- 不宣称后续能力已完成；
- 不引入大规模未使用平台；
- 不把未来版本实现偷渡到当前 Scope。

---

# 11. Provider、成本与外部服务治理

## 11.1 Provider 授权

Stage / Goal Contract 应明确：

```yaml
provider_authorization:
  allowed:
  provider:
  model_roles:
  maximum_logical_calls:
  retry_policy:
  fail_fast_condition:
  data_sent:
  evidence_to_record:
```

无明确授权时，默认不进行新的正式 Provider 运行。

---

## 11.2 不得机会性重跑

出现质量不佳、Provider Failure 或结果不符合预期时，不得为了获得“更好结果”而未经授权：

- 重采样；
- 增加模型调用；
- 改 Prompt 后继续跑；
- 更换 Provider；
- 用本地手工答案替代；
- 丢弃失败样本。

是否重跑应由 Contract 或上级 Session决定。

---

## 11.3 Provider Failure

Provider Failure 应记录：

- 请求身份；
- Provider / Model；
- 超时或错误类型；
- 已发生逻辑调用数；
- 是否有部分结果；
- 是否触发 fail-closed；
- 是否满足重试条件；
- 是否影响算法质量判断。

Provider Failure 不自动等于：

- 实现失败；
- 算法退化；
- Case 有效通过。

---

# 12. 数据、Frozen / Held-out 与污染控制

## 12.1 数据访问合同

Contract 应明确：

- 可访问的开发 Case；
- 可访问的 Held-out；
- 可访问的 Gold；
- 是否允许模型 Runtime 读取；
- 是否允许执行 Session查看；
- 谁能进行最终 Review；
- 运行产物如何隔离。

---

## 12.2 Frozen / Held-out 原则

- Production Runtime 不得读取 Gold；
- Candidate 生成不得读取用于判断自己的 Held-out Gold；
- Judge / Split / Evaluation Identity 属于受保护边界；
- 需要强隔离时创建专项 Eval Session；
- 不为所有普通 Goal 强制最高级隔离；
- 是否消耗正式有效 Run，由当前 Eval Contract 规定。

---

## 12.3 无效运行不得污染结论

如果运行在打开 Gold、数据损坏、Judge 无效或身份不完整后才暴露问题，应标记相应 Invalid Run。

不得：

- 将无效运行指标混入正式汇总；
- 用报告修补缺失身份；
- 将无效运行写成质量失败；
- 因无效运行失败而自动调整算法。

---

# 13. 证据类型

## 13.1 Source Evidence

- 源码；
- Diff；
- Commit；
- Schema；
- Migration；
- Prompt；
- 配置；
- Upstream 固定版本。

证明“实现了什么”。

---

## 13.2 Mechanical Evidence

- Unit Test；
- Integration Test；
- Type / Lint；
- Deterministic Validator；
- Migration Test；
- Idempotency Test；
- Crash / Resume Test；
- Replay；
- Static Check。

证明“合同在机械条件下如何运行”。

---

## 13.3 Product Runtime Evidence

- 真实 Fast / Deep / Research Case；
- Provider 输出；
- 用户可见页面；
- Citation；
- Trace；
- Artifact；
- Memory / Corpus 状态变化；
- 实际 Failure / Recovery。

证明“真实产品行为”。

---

## 13.4 Evaluation Evidence

- Dataset；
- Split；
- Environment；
- Rollout；
- Judge；
- Metrics；
- Invalid Run 记录；
- Related / Unrelated Regression；
- Negative Transfer。

证明“候选与 Baseline 的比较”。

---

## 13.5 Human Decision Evidence

- 用户批准；
- HITL；
- Memory Correction；
- Candidate Promotion；
- 阶段接受；
- Roadmap 决定。

证明“人类作出了什么正式决定”。

---

## 13.6 Report

Implementation Report、Research Report 和 Closeout 是证据索引，不是独立事实来源。

报告必须可以指向：

- 文件；
- Commit；
- 命令；
- Run ID；
- Trace ID；
- Artifact ID；
- Screenshot / UI；
- 用户决定。

---

# 14. 结果分类

每次正式运行或阶段结果应使用明确分类。

## 14.1 `valid_success`

运行有效，当前 Contract 的目标被满足。

---

## 14.2 `valid_partial`

运行有效，只满足部分目标。

必须明确：

- 满足了什么；
- 缺少什么；
- 缺口是产品范围、Evidence、成本还是运行限制；
- 是否可正式部分接受。

---

## 14.3 `valid_insufficient`

运行有效，但权威 Evidence 不足以完成回答或研究目标。

这可以是正确产品行为，不等于系统失败。

---

## 14.4 `product_quality_failure`

运行有效，但：

- 回答不正确或不够有用；
- 覆盖不足；
- 错误停止；
- 搜索策略不佳；
- 用户可见行为不达标。

---

## 14.5 `implementation_failure`

代码、Schema、Migration、状态机或逻辑错误导致结果无效或不符合合同。

---

## 14.6 `provider_failure`

Provider 超时、服务错误、输出耗尽、响应不可解析或其他外部模型问题。

应与实现质量分开记录。

---

## 14.7 `infrastructure_invalid_run`

环境、依赖、文件、索引、数据库、网络或 Runner 无法形成有效运行。

---

## 14.8 `evaluation_invalid_run`

Judge、Gold、Split、Environment Identity、Scaffold Fingerprint 或评测流程无效。

---

## 14.9 `not_exercised`

能力存在或被规划，但本轮没有真正触发。

示例：

- 没有发生 Crash，不能证明 Crash Recovery；
- 没有执行 Rollback，不能证明 Rollback；
- 没有产生冲突，不能证明 Conflict Resolution；
- 没有用户拒绝，不能证明 Reject 路径。

---

## 14.10 `unproven`

实现存在且可能运行，但现有证据不足以证明：

- 正确性；
- 泛化；
- 质量；
- 延迟改善；
- 负迁移；
- 真实 Provider 行为。

---

## 14.11 混合结果

一个阶段可以同时包含：

```yaml
implementation: accepted
online_quality: unproven
provider_case: provider_failure
rollback: not_exercised
```

不得强制压缩成一个模糊的“基本通过”。

---

# 15. 有效运行的最低完整性

正式 Run 是否有效，至少检查：

## 15.1 运行前

- Baseline 身份完整；
- Contract 授权；
- 数据和 Split 正确；
- Provider / Model 正确；
- 工作区可归因；
- 输入未被污染。

## 15.2 运行中

- 工具和 Provider 调用可追踪；
- 没有超出权限；
- 没有读取禁止数据；
- 没有人工修改中间结果；
- Crash / Retry / Resume 事件被记录。

## 15.3 运行后

- 结果和 Trace 完整；
- Run ID / Attempt ID 可解析；
- Citation / Source Version 可核验；
- Judge 身份完整；
- 失败未被静默丢弃；
- 成本和调用数可核对。

缺失关键完整性时，应分类为 Invalid Run 或 Unproven，而不是补写结论。

---

# 16. Pause Conditions

出现以下任一情况，执行 Session必须暂停并交回上级 Session。

## 16.1 权威和 Baseline

- 权威文件冲突；
- Baseline Commit 不存在或不匹配；
- Working Tree 无法归因；
- 当前 Schema / Index / Corpus 身份不清；
- 旧报告与真实源码冲突。

## 16.2 Scope

- 需要修改未授权模块；
- 需要跨入后续版本；
- 需要改变长期功能目标；
- 需要破坏 Protected Invariant；
- Goal 实际变成通用平台建设。

## 16.3 上游和 License

- License 不明确；
- 官方源码与文档冲突；
- 目标机制只存在于宣传、未合并 PR 或 Roadmap；
- 需要复制大段代码但来源记录不足；
- 上游维护状态明显变化。

## 16.4 资源和安全

- 需要大型模型或数据集；
- 需要高成本 Provider / API；
- 需要新凭据或私有数据；
- 需要执行危险安装脚本；
- 需要不可逆外部写操作；
- 可能泄漏私有 Query、Answer、Evidence 或密钥。

## 16.5 数据和 Migration

- Migration 无法回滚；
- 需要修改正式用户数据；
- 新对象破坏旧 Artifact；
- Source Version / Citation Identity 可能失效；
- Memory 写入可能污染用户事实。

## 16.6 Eval

- 需要未授权访问 Held-out / Gold；
- Judge 或 Split 无效；
- Candidate 需要修改自己的 Verifier；
- Experiment Identity 缺失；
- 正式 Run 配额或预算不清。

## 16.7 No-progress

- 重复研究没有产生新判断；
- 连续实现循环未改善失败；
- 多次 Provider Failure 超过合同；
- 根因无法归因；
- 需要改变 Contract 才能继续。

---

# 17. 阶段验证策略

每个 Stage 不必使用所有验证层，但必须按风险选择。

```text
Contract Check
→ Mechanical Tests
→ Integration Tests
→ Real Product Case
→ Failure / Recovery Case
→ Regression
→ Human Review
```

## 17.1 纵向产品闭环优先

阶段应优先证明：

```text
用户能够完成什么新任务
```

而不只是：

```text
新增了哪些抽象类、表和治理文件
```

---

## 17.2 真实失败必须实际触发

如果阶段目标包含：

- Resume；
- Retry；
- Cancel；
- Idempotency；
- HITL；
- Conflict；
- Rollback；

至少要选择其中由 Contract 明确要求的路径实际触发。

不能只测试 happy path 后声称整个可靠性目标完成。

---

## 17.3 回归边界

根据改动选择：

- `/search`；
- `/ask Fast`；
- `/ask Deep`；
- Citation；
- Transcript Authority；
- Existing Artifact；
- Database Migration；
- UI；
- Provider Envelope；
- Trace。

不要求所有小改动每次运行全量回归，但高风险 Stage 必须覆盖相关旧路径。

---

# 18. V5 各子版本的证据重点

## 18.1 V5-A

重点证据：

- Task / Attempt / Checkpoint 身份；
- 真实进程中断和恢复；
- 副作用 Idempotency；
- Goal Audit 只使用可见 Evidence；
- No-progress；
- HITL；
- Retry / Cancel；
- 不重复 Provider 或付费动作。

没有实际中断时，Recovery 标记 `not_exercised`。

---

## 18.2 V5-B

重点证据：

- L1/L2/L3 Lineage；
- Artifact 可下钻到字幕；
- Source Version / Staleness；
- Direct Reuse / Incremental Refresh；
- Corpus Model 不作为事实 Citation；
- User Memory 显式与推断分离；
- Migration 和旧数据兼容；
- Memory 写入、修改和删除可审计。

---

## 18.3 V5-C

重点证据：

- 用户确认 Gate；
- 隐式反馈只形成 Candidate；
- Profile 版本和 Rollback；
- 个性化确实影响回答、搜索或路由；
- 不错误推断“收藏/搜索=掌握”；
- Corpus Prior 不造成搜索窄化；
- 主动提醒有可解释 Trigger 且可关闭。

---

## 18.4 V5-D

重点证据：

- Raw Trace、Diagnosis、Hypothesis、Candidate、Active Skill 分离；
- Step-level Attribution；
- Baseline / Candidate 配对；
- Related Task 泛化；
- Unrelated Regression；
- Negative Transfer；
- Progressive Disclosure；
- Promotion / Rollback；
- Candidate 不能修改 Judge、Split、Verifier 或 Promotion Gate。

---

# 20. 阶段验收包

主 Session验收所需的最小包：

```text
1. 已接受的 Version Charter
2. 当前 Stage / Goal Contract
3. Implementation Report
4. 实际 Diff / Commit
5. 测试与运行证据
6. Invalid / Failure / Unproven / Not Exercised 记录
7. 必要的 Upstream Adoption Decision
8. 当前 Git 与 Baseline 状态
```

只有发生下列情况才额外要求：

- Blocking Report；
- Handoff；
- Independent Review；
- Frozen Eval Report；
- Migration Recovery Report；
- Roadmap Reconsideration Memo。

# 21. Git 与产物边界

## 21.1 正式仓库内容

适合提交：

- 产品源码；
- 正式测试；
- Migration；
- Version Charter；
- Contract；
- 接受后的 Report / Closeout；
- Program Current State / Decision Ledger；
- Registry；
- 必要的 Attribution / Notice；
- 小型、可复现的测试 Fixture。

---

## 21.2 默认不提交

- 整个上游仓库；
- 大型论文 PDF；
- 大模型；
- 大型数据集；
- Raw Provider Response；
- 私有 Query / Answer；
- 用户 Evidence 正文；
- API Key；
- 临时 Cache；
- 大型运行 Trace；
- 临时 Spike 环境。

可以通过：

- `.gitignore`；
- 本地 Reference 目录；
- Artifact Manifest；
- Hash；
- Run ID；

保留可追踪性。

---

## 21.3 正式证据与忽略证据

不提交 Raw Evidence 不等于没有证据。

报告应记录：

- 本地路径或 Artifact ID；
- Hash；
- 生成命令；
- Run ID；
- 是否包含私有内容；
- 复现条件。

不得为了方便审查，将隐私或密钥写入正式仓库。

---

# 22. 安全、隐私与 Provenance

## 22.1 隐私

必须避免在：

- Report；
- Trace；
- Git；
- Research Log；
- Registry；

保存不必要的：

- 用户私人 Query；
- 完整 Answer；
- 原字幕大段正文；
- Provider Raw Response；
- API Key；
- Cookie；
- 账号信息。

需要证明行为时，优先保存：

- ID；
- Hash；
- 有界摘要；
- 机械指标；
- Redacted Trace。

---

## 22.2 上游 Provenance

任何复制、改写或依赖都应记录：

```yaml
provenance:
  project:
  official_url:
  license:
  upstream_commit:
  original_files_or_symbols:
  adoption_mode:
  local_modifications:
  attribution_required:
```

---

# 23. 防止治理膨胀

## 23.1 默认最小文件集

普通 Stage 默认只需要：

```text
Stage / Goal Contract
Implementation Report
主 Session 验收记录
```

Version 级：

```text
Version Charter
Current State
Decision Ledger
Final Closeout
```

---

## 23.2 不默认创建

- 每个 Goal 的独立 Charter；
- 每个小改动的 Readiness Report；
- 多份重复 Gate；
- 每个失败的长篇 Handoff；
- 每次浏览的研究日志；
- 所有 Goal 的独立主 Session；
- 大型通用 Eval 平台。

---

## 23.3 治理停止信号

出现以下情况应主动精简：

- 文档增长快于产品能力；
- Codex 主要时间用于同步状态；
- 同一事实在多份文件重复维护；
- 每个小 Commit 都等待正式验收；
- 用户可见闭环长期没有推进；
- 为“证明严谨”不断扩大 Dataset 和 Gate；
- Session 数量本身成为管理负担。

---

# 24. 研究与实现的推荐完整流程

```text
1. 当前子版本确认研究问题
2. 检查 Registry 与本地 Reference
3. 必要时自主获取官方项目
4. 固定 Commit / Release / License
5. 开展有界研究或 Spike
6. 追加材料性 Research Log
7. 形成 Adoption Decision
8. 将采用范围写入 Stage / Goal Contract
9. 固定风险匹配的 Baseline
10. 实施
11. 运行机械测试和真实 Case
12. 记录有效、失败、Invalid、Unproven、Not Exercised
13. 形成 Implementation Report
14. 向主 Session提交阶段验收
15. 主 Session独立核验
16. 接受后更新 State、Ledger、Registry 和 Git
```

---

# 25. 高风险动作前自检

执行 Session在下载、复制、运行 Provider、Migration、Held-out、Promotion 或提交验收前必须能回答：

1. 当前研究或实施是否已被 Version Charter / Contract 授权？
2. 本地是否已有适用上游副本？
3. 上游官方来源、Commit 和 License 是否明确？
4. 下载是否只是研究，还是已获实施授权？
5. 采用方式是什么？
6. 当前 Baseline 风险级别是什么？
7. Protected Invariants 是什么？
8. Provider / 数据 / Held-out 权限是否明确？
9. 哪些失败路径必须实际触发？
10. 本轮哪些结果可能是 `not_exercised` 或 `unproven`？
11. 报告将指向哪些真实证据？
12. 是否正在跨入后续版本或通用平台建设？
13. 是否需要暂停并交回上级 Session？

# 27. 一句话摘要

```text
当前子版本 Session可以在授权范围内自主获取并深入研究上游，
也可以充分复用成熟代码；但研究、采用、实施、验证和正式接受必须分离。

任何阶段只有在 Baseline 可归因、证据真实存在、失败和无效运行被准确分类、
受保护边界未被破坏，并经主 Session独立验收后，才能成为拾流的正式结果。
```
