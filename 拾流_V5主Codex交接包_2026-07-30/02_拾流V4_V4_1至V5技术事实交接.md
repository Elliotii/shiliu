# 3. V4 当前产品表面

## 3.1 `/search`

`/search` 保留为直接证据搜索入口，主要用于：

- 搜索原字幕 Evidence；
- 手动查证；
- Debug；
- 与回答路径对比；
- Demo。

它不是被 `/ask` 替代的旧页面。

---

## 3.2 `/ask`

`/ask` 是统一问答入口，显式提供：

```text
快速回答 | 深入搜索
```

当前产品规则：

- Fast 默认；
- Deep 必须由用户显式选择；
- Fast 返回 `partial` 或 `insufficient` 时，可以保留 Query 和 Filters 继续 Deep；
- 系统不会后台自动从 Fast 升级到 Deep；
- 最终 Answer 一次性返回；
- V4/V4.1 没有 Token-by-token Answer Streaming。

---

## 3.3 `/search` 与 `/ask` 的共用和分离

共用：

- 权威字幕来源；
- Evidence Card；
- 字幕折叠展开；
- 时间格式；
- Bilibili 时间点跳转；
- 薄 Evidence Renderer。

保留独立：

- 页面状态机；
- 搜索结果与最终回答的产品语义；
- Fast/Deep 运行和 Trace；
- `/search` 的直接查证定位。

V5 不应为了新增 Research Workspace，破坏 `/search` 的专业查证用途或 `/ask` 的现有产品闭环。

---

# 4. 共享 Ask 输出合同

Fast 与 Deep 当前共用：

```yaml
AskResponse:
  run_id:
  mode: fast | deep
  status: complete | partial | insufficient
  answer_blocks:
    - text:
      citation_ids: []
  citations: []
  limitations: []
  termination_reason:
  trace_summary:
```

## 4.1 `answer_blocks`

`answer_blocks` 是答案正文的唯一结构化事实源。

不得同时维护：

```text
自由 Answer 正文
+
另一套独立 Claim 真相
```

V5 如增加 Research Artifact、Topic Page 或 Grounded Fact，应在明确的 Lineage 合同下派生，不应使当前 Answer 重新出现两套互相漂移的正文事实源。

---

## 4.2 `status`

`status` 表示回答充分度：

```text
complete
partial
insufficient
```

它不表示程序是否崩溃，也不表示 Agent 为什么停止。

---

## 4.3 `termination_reason`

当前停止原因包括：

```text
answer_ready
budget_exhausted
no_new_evidence
repeated_search
provider_error
evidence_unavailable
```

必须保持：

```text
回答充分度
≠
运行终止原因
```

V5-A 扩展 ResearchTask 状态时，不能把 Task Status、Blocker、Answer Sufficiency 和 Runtime Termination 混成一个枚举。

---

# 5. 事实权威与材料分层

## 5.1 事实权威

V4/V4.1 的核心不变量：

```text
当前 Source Version 可验证的原字幕 / ASR
=
最终事实权威
```

最终事实 Context 只能由：

```text
TranscriptEvidenceSpan
```

及其当前 Source Version 构成。

---

## 5.2 Navigation-only 材料

以下材料可用于：

- 视频导航；
- Query 扩展；
- 候选视频选择；
- 低成本预理解。

但在 V4/V4.1 中不能作为最终事实 Citation：

- 标题；
- 简介；
- AI 总结；
- User Notes；
- 整理稿；
- 其他元数据。

语义标签应保持：

```yaml
authority: navigation_only
citation_allowed: false
```

V5 若未来引入用户自有知识、Notes 或 Artifact，必须建立新的明确权威类型和 Lineage；不得静默把 Navigation 材料升格为原字幕事实来源。

---

# 6. `TranscriptEvidenceSpan` 与 Stable Citation

## 6.1 Stable Citation Identity

Citation 与 Retrieval Candidate Identity 解耦，至少绑定：

```yaml
StableCitationIdentity:
  source_artifact_id:
  source_version:
  timeline_run_id:
  ordered_segment_ids:
```

关键性质：

- 更换 Retrieval Method 不应无意义改变 Citation；
- 更换排名策略不应无意义改变 Citation；
- UI 展示扩窗不应改变事实 Citation；
- 字幕文本、时间或 Source Version 变化应使旧 Citation 正确失效。

---

## 6.2 Evidence 与 Display Context 分离

事实 Citation 对应确定的权威 Segment 集合。

UI 可以为阅读体验扩窗，但：

```text
展示扩窗
≠
事实范围扩张
```

V5 的 Topic Page、Artifact Reuse、Research Thread 或 Memory 下钻必须保留该边界。

---

## 6.3 Source Version Revalidation

Fast 和 Deep 在 Answer 返回前都必须重新验证 Source Version。

如果 Evidence 已过期：

- 不得继续作为当前事实；
- Stale Hit 应跳过并记录；
- 旧 Artifact 未来若复用，也必须先完成相应版本校验。

---

## 6.4 `quote_excerpt` 不是完整 Citation

V4 Integration Review 曾发生一次人工误判：审阅者只查看有界 `quote_excerpt`，误认为 Citation 不支持 Answer。

主 Session 按以下信息重建完整当前字幕后确认支持关系：

- 当前 Source Version；
- 相同 Stable Citation ID；
- 完整时间范围和 Segment。

因此冻结规则：

> 有界 Excerpt 只用于审阅便利，不是完整 Citation。若支持内容可能位于截断范围外，必须按 Stable Citation 重建当前权威字幕后判断。

V5 的 Artifact Review、Memory Review 和 Eval 不得仅依据截断摘要作最终 Supportedness 判断。

# 7. Fast Grounded RAG 技术事实

## 7.1 当前流水线

```text
User Query
→ Query Analysis
→ 最多两个 Bounded Rewrites
→ 每个不同 Query 一次 Retrieval
→ SearchExecution
→ Evidence Materialization
→ 当前版本 TranscriptEvidenceSpan
→ Transcript-only Context
→ Structured Answer Blocks
→ Stable Citation
→ Source Version Revalidation
```

---

## 7.2 调用预算

```yaml
fast_budget:
  query_analysis_calls: 1
  answer_calls: 1
  repair_calls: max_1
  iterative_search: false
```

“最多两个 Rewrites”不等于多轮 Agentic Search。Fast 是固定有界 Pipeline。

---

## 7.3 `SearchExecution`

V4 将 Retrieval 执行和产品投影/证据物化分离：

```text
Search Execution
→ Raw Retrieval + Product Projection
→ Evidence Materializer 消费已有执行结果
```

目标是避免对同一 Query 重复 Retrieval。

关键兼容点：

- `execute_search()` 与 `materialize_execution()` 分离；
- `search_library()` 保留兼容包装；
- Evidence Materializer 不应自行再次召回。

V5 在构建 Artifact Reuse、ResearchTask 或 Corpus Intelligence 时，应复用或清晰扩展这一单次执行语义，不应重新引入隐藏重复检索。

---

## 7.4 Answer Repair

当前 Answer：

- 最多一次 Same-context Repair；
- Repair 与 Transport Retry 分开；
- Repair 后仍不合规则整体 Fail-closed；
- 不做 Block Salvage。

V5 若新增 Outer Audit 或 Research Continuation，不能把它与当前 Same-context Answer Repair 混为一类：

```text
Answer Repair
= 同一 Evidence Context 下修复结构或合同

Research Continuation
= 因证据缺口继续获取新 Evidence
```

---

## 7.5 Provider Failure 边界

Goal 1 Integration Repair 已区分：

- 可重试 Transport Failure；
- 不应重试的失败；
- Answer Repair；
- Provider Usage；
- Trace 语义。

V5 必须保留：

```text
Transport Retry
≠
Answer Repair
≠
Research Retry
≠
Task Resume
```

# 8. Deep Independent Agentic Search 技术事实

## 8.1 独立性的准确含义

Deep 不先执行 Fast，也不依赖 Candidate Builder 作为入口。

当前流程：

```text
Original User Query
→ Navigation
→ Focused Transcript Search
→ Transcript Window Read
→ Observation
→ Planning / Replanning
→ Evidence Accumulation
→ Conditional Stop
→ Shared Grounded Answer
```

准确描述：

```text
Agentic Navigation / Retrieval
+
共享 Transcript-grounded Answer
```

Fast 和 Deep 的差异位于 Retrieval / Orchestration 层；最终 Evidence、Answer、Citation、Validation 和 UI 合同共享。

---

## 8.2 Deep Runtime State

当前至少维护：

- Original Query；
- Open Questions；
- Resolved Questions；
- Evidence Spans；
- Visited Video IDs；
- Visited Segment IDs；
- Previous Queries；
- Decision Rounds；
- Tool Calls；
- Consecutive No-new Evidence；
- Events；
- Termination Reason；
- Budget。

这些是运行时工作清单和 Guard 输入，不是 Gold Aspect，也不是长期用户 Memory。

---

## 8.3 Agent Action

DeepSeek 使用结构化 JSON / Pydantic Action，而不是依赖 Native Tool Calling。

当前动作包括：

- Navigation Search；
- Transcript Search；
- Transcript Window Read；
- Finish；
- Stop。

V5-A 可以扩展 ResearchTask 和 HITL，但不应默认将现有 Action 合同替换成通用 Agent SDK 或开放式工具平台。

---

## 8.4 Deep 预算

```yaml
deep_budget:
  decision_rounds: max_6
  tool_calls: max_12
  focused_video_limit: 8
  consecutive_no_new_evidence: 2
  final_context_chars: 12000
  total_runtime_seconds: 360
  search_phase_cutoff_seconds: 150
  final_answer_reserve_seconds: 210
```

重复 Query、重复 Segment、No-new Evidence、Context 和时间上限由确定性代码控制，不能只靠 Prompt。

---

## 8.5 Deadline 与 Stop 语义

Goal 2 Integration Review 修复并冻结：

- Finalization Deadline 使用真实上界；
- Initial Answer 与一次 Repair 共用 Answer Deadline；
- Deadline Exhaustion 映射为 `budget_exhausted`；
- 普通 Provider Network Error 映射为 `provider_error`；
- Deadline 耗尽不触发无意义 Transport Retry；
- `FinishAction` 与 `StopAction` 语义分离；
- Stop 有 Evidence 时可以使用已有证据返回 `partial`；
- 无 Evidence 时返回 `evidence_unavailable`。

V5-A 的 Typed Blocker 和 Continuation 必须建立在该语义之上，而不是重新用一个模糊 `failed` 覆盖所有结果。

# 13. V4 轻量真实 Eval

## 13.1 初始矩阵

普通 Query 六条：

- 两条直接事实 / 单主题；
- 一条上下文问题；
- 一条跨视频问题；
- 一条 Partial-support；
- 一条 No-evidence。

运行：

```yaml
fast_runs: 6
deep_runs: 4
manual_reviews: 10
dimensions:
  - supportedness
  - usefulness
  - coverage
  - status_honesty
```

结果逐 Case 保留，不计算生产 SLA 或单一总分。

---

## 13.2 Integration Repair

真实 Eval 发现并修复：

1. 有限 Retrieval/Context 被表述成整个收藏库不存在；
2. `status_termination_valid` 曾被硬编码；
3. Navigation Citation 检查可能空洞通过；
4. 有界 Excerpt 可能造成 Supportedness 人工误判。

修复后：

- Prompt 明确有限样本不能证明全库缺失；
- `insufficient` 强制空 Answer/Citation；
- 无证据说明必须范围诚实；
- Limitations 不能承载无 Citation 的材料性事实；
- Checker 真正验证 Schema、Status/Termination、Answer Shape、Citation Resolution 和当前字幕重建；
- 加入负向测试证明 Checker 会失败；
- 只复跑明确授权的 3 Fast + 1 Deep；
- 原初始结果保持不变；
- 不通过重采样把失败改写为成功。

---

## 13.3 继承到 V5 的 Eval 纪律

应继续保留：

```text
小型真实 Eval
→ 保留成功与失败
→ 只对重复且材料性的失败进行有界修正
```

不应自动恢复：

- V3.5 式大型 Frozen Governance；
- 多 Reviewer 常驻审批；
- 单一大总分；
- 每个内部判断独立 Gate；
- 为普通 Goal 建设通用 Eval Platform。

# 14. V4 Integration Review 的工程经验

主 Session / Goal Session 分工在 V4 中产生了实际价值：

- Goal 2 的 Answer Reserve、Deadline 分类和 Finish/Stop 问题由主 Session发现；
- Goal 3 的全库否定和 Checker 空洞通过由主 Session发现；
- Citation Excerpt 的人工误判由主 Session按当前 Source Version 重建后纠正。

因此 V5 治理继续采用：

```text
执行 Session负责纵向实现
主 Session负责独立阶段验收
```

# 16. V4.1 Phase 0：Crash-safe E2E Harness

# 17. V4.1 H1：Shared Grounded Answer Boundary

# 18. V4.1 H2：Deterministic Deep DecisionView

- Visited Sets；

- 完整 Segment Set。

# 21. 当前已知风险与未证明项

V4 代表性 Window/Replanning Case 的四次 Agent Decision 曾使用约 58,396 Tokens。

Deep 继续应由用户显式选择，除非未来 V5-C 在有证据基础上实现路由。

Goal 3 六条 Fast 真实运行均发生 Context Truncation。

当前没有重复材料性证据证明关键 Evidence 稳定落在预算之外，因此 V4 没有触发：

- Reranker；
- Automatic Context Compaction；
- 新 Context Selector。

V5 不应仅因“曾经出现 Truncation”自动建设这些能力。


V5-A Outer Audit 或 V5-B Artifact 可以改善有用性，但不得降低 Grounding 边界。

- Agent Action Schema 漂移；
- Answer 长度上限；
- Provider Error；

- 结构化输出不稳定。

- Source Identity；
- Source Version；
- Segment；
- Quote；
- 时间跳转。

- 不证明大规模 Recall 已解决；
