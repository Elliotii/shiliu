# 我做 AI Agent 一年，90% 在做表面功夫——直到我换了思路

> 人工整理的 V0 验收参考，不是当前 Provider 的正式生成结果。

## 一句话结论

AI Agent 开发真正的效率提升，不只来自更快地生成代码，而来自把系统改造成可观察、可操作、可重复验证的架构，让 Coding Agent 能够围绕明确的验收标准自动开发、测试、比较并持续收敛。

## 核心观点

1. AI 让生成代码越来越便宜，但验证 Agent 行为是否正确仍然昂贵，手动测试因而成为主要瓶颈。
2. 可以借鉴芯片验证行业：工程价值会从单纯实现功能，转向设计回归测试、检查点、覆盖度和验证体系。
3. 面向 Agent 的系统不能只提供给人操作的 UI，还要允许后端脱离前端独立运行，并暴露工作流、工具调用和中间状态。
4. Agent 回归测试应使用两层裁判：确定性内容交给 Assertion，难以硬判断的自然语言和行为质量交给上下文干净的 LLM Supervisor。
5. 将 Happy Path、真实用户案例和 Feature Flag 组合起来，可以比较功能开启前后的差异，发现改进和回归。
6. 最终可以让 Codex 一类 Coding Agent 先定义测试和开关，再实现功能、运行回归、读取反馈并反复修改，形成自动收敛闭环。

## 详细笔记

### 手动验证成为 Agent 开发瓶颈　00:00

作者回顾自己的 AI Agent 开发时间，认为真正用于写代码和设计的时间只占少数，大部分时间消耗在打开网页、输入测试数据、观察工作流，并依靠人工判断行为是变好还是变坏。Agent 本身具有不确定性，一处很小的 Prompt 修改也可能造成难以直接观察的回归。

### 验证的不对称性　01:25

视频提出“生成逐渐便宜、验证仍然昂贵”的不对称。作者的目标不是继续增加手动检查，而是把依赖肉眼和感觉的问题改造成自动、可重复的验证系统。一旦结果是否正确能够被可靠验证，后续尝试和改进就更适合交给 AI。

字幕在这一部分对英文人名和定律名称存在明显识别问题，正式整理时需要保守修正或标记不确定，不应根据发音自行补造引用。

### 借鉴芯片设计与验证体系　02:31

芯片流片后的错误代价极高，因此芯片行业长期投入大量资源构建验证体系，包括回归测试、检查点和覆盖度。作者认为 AI Agent 工程正在出现类似变化：代码生成成本下降以后，能否设计一套验证每次改动的体系，会成为新的工程价值。

### 先让系统对其他 Agent 友好　04:04

作者没有从编写测试用例开始，而是先改造被测 Agent。原系统主要通过网页 UI 使用，离开人的点击和观察就难以运行。为了让 Codex 等 Coding Agent 自动测试，系统需要满足三个条件：脱离 UI 后仍可运行、保留足够的中间状态，以及提供 Agent 能主动调用的接口。

作者比较了两条路线：通过多模态或 MCP 模拟人的网页操作，以及彻底分离前后端并把后台能力暴露为命令行接口。他选择后者，让前端主要负责展示和人工操作，后端可以独立、长期运行。

### 为 Agent 设计专门接口　06:57

视频引用 SWE-agent 的 Agent-Computer Interface 思路，强调 AI Agent 是一类不同于人的用户。接口是否便于 Agent 获取信息和执行操作，可能比单纯更换更强模型更影响最终表现。

### 两层回归测试裁判　07:43

新增工具或功能时，作者先定义期望工作流，即 Happy Path。由于 Agent 输出包含自然语言和运行路径，传统的单一通过或失败判断并不足够，因此裁判被拆成两层：

- 确定性 Assertion 检查工具是否触发、中间状态数量和明确覆盖条件。
- LLM Supervisor 评估无法用硬规则判断的行为质量。

Supervisor 不参与开发过程，只接收正确预期和实际结果，尽量避免受到实现上下文干扰。对于没有唯一答案的内容，作者倾向于让它量化比较变化，而不是简单判断绝对对错。

### 累积案例并使用 Feature Flag　10:06

回归集合既包含开发新功能时形成的 Happy Path，也包含从真实用户和测试中收集的意外输入。每个新功能配备开关后，可以让开启和关闭两个版本运行同一套测试，从而观察哪些指标改善、哪些行为发生回归。

### 让 Coding Agent 形成开发闭环　11:02

在完整体系中，Coding Agent 的任务顺序变为：先设计回归测试，再设计功能开关，然后实现代码；实现后分别运行开启和关闭版本，读取回归结果并继续修改，直到满足验收要求。人的主要职责逐渐转向定义什么算正确，以及设计一个可以可靠验证的环境。

### 不要为了使用 AI 而降低效率　12:24

作者最后强调，这套方案不是所有项目必须照搬的固定答案。更重要的是识别自己工程中反复、烦躁并吞噬时间的环节，再选择适合的自动化方式。如果使用 AI 后完成同一件事反而耗费更多时间，就没有实现真正的效率提升。

## 可执行事项

- 统计当前项目中用于实现、手动测试和重复验证的时间，找出主要瓶颈。
- 检查核心后端能否脱离 UI 独立运行，并通过 CLI 或稳定接口被自动调用。
- 为工作流记录工具调用、输入输出和关键中间状态，使 Agent 能够读取执行过程。
- 为新增功能定义 Happy Path，并优先使用确定性 Assertion 验证可硬判断的条件。
- 对自然语言和模糊行为单独设计 LLM Supervisor，并保持其评估上下文独立。
- 使用 Feature Flag 比较功能开启和关闭时的同一套回归结果。
