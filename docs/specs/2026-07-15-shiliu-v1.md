# 拾流 Shiliu V1：多来源收藏夹与快速／正式双路径

## Status

Approved

## Goal

在保留 V0 本地单用户架构的前提下，增加：

1. 通过公开 B 站收藏夹 URL 添加多个内容来源。
2. 按账号、收藏夹或全部来源浏览内容。
3. 首页按真实收藏时间优先展示最新收藏。
4. 区分“立即同步快速结果”和“定时同步正式结果”。
5. 对快速结果执行可恢复的后台精修。
6. 增加同步进度、模型角色配置和必要的 B 站访问节流。

V1 必须保证现有 V0 数据、页面内容和自动同步不会因升级丢失。

## Context and Current State

### 当前仓库事实

- `src/shiliu/config.py:AppConfig` 当前只保存一个 `favorite_id`、一个模型和一个 Base URL。
- `src/shiliu/app.py:Application` 当前创建一个 `BilibiliAdapter`、一个 `PipelineService` 和一个绑定单收藏夹的 `SyncService`。
- `src/shiliu/db.py:SCHEMA_VERSION` 当前为 1；视频身份由 `platform + source_id + part` 唯一约束。
- `src/shiliu/sync.py:SyncService` 当前只扫描一个收藏夹，并用进程文件锁防止并发执行。
- `src/shiliu/pipeline.py:PipelineService` 当前每个视频固定执行一次字幕整理和一次摘要生成。
- `src/shiliu/llm.py:OpenAICompatibleProvider` 当前只有一个 OpenAI-compatible 模型配置，默认调用超时为 120 秒。
- `src/shiliu/artifacts.py:ArtifactStore` 当前只保存一份 `transcript.*` 和一份 `summary.*`。
- `src/shiliu/web.py:sync_now` 当前“立即同步”保持 HTTP 请求直到完整同步结束。
- `src/shiliu/launchd.py:install_launch_agent` 当前每小时执行一次 `shiliu sync --scheduled`。
- 规格批准前测试基线为 `25 passed, 1 warning`。

## Scope

### 多来源管理

- 使用一个已登录的小号凭据读取多个收藏夹来源。
- 支持通过公开收藏夹 URL 添加其他账号的公开收藏夹。
- 自动读取账号名称、账号 ID、收藏夹名称、收藏夹 ID 和视频数量。
- 支持启用、暂停、立即同步和移除单个来源。
- 支持查看全部来源，或按账号、收藏夹筛选。
- 同一个视频来自多个收藏夹时只生成一张内容卡片，同时显示多个来源标签。

### 历史导入

添加来源时提供：

- 只处理添加之后新增的。
- 导入最新 10 条。
- 导入最新 30 条。
- 导入最新 100 条。
- 导入自定义数量。
- 导入全部历史内容。

默认选择“只处理添加之后新增的”。

### 双处理路径

- “立即同步”优先生成快速版。
- 定时同步发现的新视频和历史积压直接生成正式版。
- 快速版在后续允许的定时周期中自动精修。
- 页面提供单视频“立即精修”。
- 快速版和正式版均保留独立结构化产物。
- 正式版完成后原子切换为正式内容。

### 模型设置

设置页分别配置：

- 快速字幕整理模型。
- 正式字幕整理模型。
- 正式摘要模型。
- Base URL。
- API Key。
- 推理强度。

推理强度在页面显式显示为 `max`。若旧配置或导入配置使用 `xhigh`，内部规范化为 `max`。

### 同步可观测性

- “立即同步”启动后立即返回任务状态，不持续阻塞浏览器请求。
- 页面显示同步阶段、当前视频、已处理数量、失败数量、历史待处理数量和经过时间。
- 关闭浏览器页面不停止后台处理。
- 重复点击不会启动相同范围的第二个同步，而是连接到已有任务状态。

## Non-goals

V1 明确不实现：

- 一个来源使用一个独立 B 站账号或独立凭据。
- 多用户、账号权限系统或远程 SaaS。
- B 站收藏、取消收藏、点赞、评论等写操作。
- 音频下载、ASR 或无字幕回退。
- 多 P 处理或多 P 摘要。
- 打开或读取视频简介中的外部链接。
- 快速版历史浏览、版本对比或人工选择版本界面。
- 任意次数的摘要版本管理。
- 自动执行“可执行事项”。
- Codex CLI、Claude Code CLI 或 Agent Runner。
- 通用 Provider 插件系统。
- DeepSeek 专用 SDK。
- Redis、Celery、消息队列、独立 Worker 服务或云端任务系统。
- 并行请求多个 B 站来源、分页、视频或字幕。
- 模型调用成本统计和成本上限。
- 为英文字幕建立专门的真实视频集成验收。
- 修改或分叉上游 `bilibili-cli`。
- React、Vue 或其他 SPA 重写。
- 保证内容处理顺序与页面展示顺序完全一致。

实现不得包含上述 Non-goals 明确排除的能力。

## Users and Key Flows

### 添加公开来源

```text
设置页
→ 输入公开收藏夹 URL
→ 只读预览账号、收藏夹和数量
→ 选择历史导入策略
→ 确认添加
→ 建立来源和成员关系
→ 按历史策略建立基线或创建待处理内容
```

预览操作不得导入视频、下载字幕或调用模型。

### 立即同步

```text
点击首页“立即同步”
→ 同步全部启用来源
→ 发现新增视频
→ 快速模型整理字幕，不启用 thinking
→ 正式摘要模型生成摘要，thinking=max
→ 页面显示“快速版”
→ 状态进入 refinement_pending
```

在某个来源页面点击“立即同步”时，只同步当前来源。

### 定时同步发现新视频或处理历史积压

```text
launchd 启动 scheduled sync
→ 串行扫描所有启用来源
→ 优先处理新收藏视频
→ 再处理本轮历史积压
→ 正式字幕模型，thinking=max
→ 正式摘要模型，thinking=max
→ 直接成为正式版
→ 页面不显示版本标识
```

### 精修快速版

```text
允许的定时同步周期
→ 发现 refinement_pending
→ 正式字幕模型重新整理原文，thinking=max
→ 正式摘要模型审查快速摘要
→ 模型决定 keep 或 revise
→ 原子切换正式原文和正式摘要
→ 页面移除“快速版”标识
```

用户点击“立即精修”时，不受 05:00–11:59 静默时段限制。

## Behavioral Requirements

### 来源 URL

接受至少以下形式：

```text
https://space.bilibili.com/<mid>/favlist?fid=<fid>&ftype=create
```

系统必须：

- 使用 URL 中的 `fid` 作为收藏夹身份。
- 从 B 站响应校验收藏夹和账号元数据。
- 拒绝缺少合法 `fid` 的 URL。
- 拒绝无法访问、已失效或非公开视频来源。
- 检测重复收藏夹；不得重复创建来源。
- 不依赖 URL 中的账号名称或用户手工输入名称。
- 不把 URL 预览视为正式导入。

### 来源状态

每个来源至少具有：

```text
active
paused
needs_auth
unavailable
cooldown
```

- `paused` 来源不参加自动同步和全局立即同步。
- 单来源页面可重新启用。
- 来源暂时不可访问时，不删除已有视频及成果。
- 移除来源只删除来源绑定关系，不删除仍被其他来源引用的视频。
- 视频不再属于任何来源时，保留已生成成果，但标记为不在当前来源中。

### 视频身份和来源关系

- 内容身份继续使用 `bilibili + BV + P1`。
- 视频和收藏夹来源为多对多关系。
- 同一 BV 出现在多个来源时不得重复下载字幕或调用模型。
- 卡片显示所有当前来源标签。
- 每个来源成员关系独立记录 `favorite_time`、来源内顺序、首次及最后观察时间和移除时间。
- 同一视频的页面展示时间取其当前来源关系中最新的有效收藏时间。

### 页面排序

全部来源和单来源页面均以“最新收藏靠前”为目标：

1. 有 `fav_time` 时，按 `fav_time` 降序。
2. 没有 `fav_time` 时，使用来源 API 返回顺序判断新旧。
3. 跨来源且缺少可比较时间时，使用 `first_observed_at` 作为近似时间。
4. 完成时间、模型处理顺序和视频发布时间不得覆盖收藏时间排序。
5. 忽略卡片保留原有排序位置。

### 历史导入

- “只处理之后新增的”将当前列表写入该来源基线，不创建内容处理任务。
- “最新 N 条”只把来源中最新 N 条加入处理范围，其余项目作为基线。
- “导入全部”把当前所有可访问视频加入处理范围。
- 重复视频复用已有卡片和成果。
- 历史导入不得改变其他来源的基线。
- 历史积压直接走正式路径，不生成快速版。
- 每轮定时任务最多处理 8 个历史积压视频。
- 新收藏视频优先于历史积压。
- 历史视频之间的 B 站读取加入 2–6 秒随机间隔。
- 页面显示历史待处理总数和本轮进度。

### 快速路径

立即同步中新发现的视频：

1. 快速字幕整理使用快速字幕模型并明确关闭 thinking。
2. 快速摘要使用正式摘要模型，thinking 开启，`reasoning_effort=max`。
3. 成功后保存快速原文和快速摘要，设置 `active_revision=fast`、`refinement_status=pending`，视频卡片显示“快速版”。

快速路径正常共调用模型 2 次。

### 正式路径

定时同步中新发现的视频和历史积压：

1. 正式字幕整理模型，thinking 开启，effort 为 `max`。
2. 正式摘要模型，thinking 开启，effort 为 `max`。
3. 成功后设置 `active_revision=refined`、`refinement_status=not_required`，页面不显示任何版本标签。

正式路径正常共调用模型 2 次。

### 精修路径

快速版后续精修：

1. 使用正式字幕整理模型和 `max` 重新生成整理原文。
2. 将精修原文、快速版摘要、视频标题、简介及简介链接交给正式摘要模型。
3. 模型返回结构化判断：

```json
{
  "decision": "keep | revise",
  "change_reasons": ["修改或保留原因"],
  "revised_summary": {}
}
```

行为：

- `keep`：正式使用精修原文和原快速摘要。
- `revise`：正式使用精修原文和模型返回的新摘要。
- 精修原文与最终摘要都成功并通过结构校验后，才允许原子切换。
- 切换完成后不再显示“快速版”或“精修版”标识。
- 快速产物继续保存在本地，但 UI 不提供入口。

快速版加精修正常最多调用模型 4 次。

### 精修状态

至少包括：

```text
not_required
pending
processing
completed
failed
```

- `pending`：卡片显示“快速版”。
- `processing`：卡片显示“快速版 · 精修中”。
- `completed`：不显示版本信息。
- `failed`：继续展示快速内容，显示“快速版 · 精修失败”，提供重试。
- 精修连续失败三次后进入 `failed`，不得隐藏仍然可用的快速版。

### 模型配置与验证

设置页必须：

- 使用 OpenAI-compatible Chat Completions。
- 继续支持 Base URL、API Key、`/models` 和手工模型名称。
- API Key 继续只保存到 macOS Keychain。
- 分别测试三个模型角色的真实小型生成请求。
- 显示每个角色是否支持所需 thinking 配置。
- 显式显示正式模型使用 `max`。
- 不在 UI 中显示 `xhigh`。
- 读取旧配置或导入配置中的 `xhigh` 时规范化为 `max`。
- 不因模型不可用而静默换用其他模型。
- 不因 thinking 参数不兼容而静默关闭 thinking。
- 配置错误时指出具体模型角色和错误原因。

### 超时与后台执行

- 快速模型调用超时允许提高到 180 秒。
- 正式模型和精修模型调用超时允许提高到 600 秒。
- UI 发起同步后返回可查询的运行 ID。
- 页面轮询持久化的运行状态。
- 浏览器关闭不停止服务器中的同步线程。
- 应用进程意外终止时，未完成阶段在下次同步中按持久化状态恢复。
- 不引入独立 Worker、队列服务或常驻任务系统。
- CLI 和 launchd 仍调用同一个同步核心函数。

### 调用串行和 B 站访问控制

- 所有 B 站收藏夹、分页、视频详情和字幕读取保持串行。
- 定时任务在取得全局同步锁前增加 60–300 秒随机启动抖动。
- 立即同步不增加启动抖动。
- 不对 LLM 精修调用增加 B 站访问抖动。
- 普通新增读取连续出现 HTTP 412 或 429 时，对发生限制的来源冷却 10 分钟。
- 处理历史积压时出现 HTTP 412 或 429 时，对发生限制的来源冷却 20 分钟。
- 一个来源失败不得删除其已有数据。
- 全局认证失败时停止所有来源；单来源不可访问或受限时记录该来源错误并继续其他来源。
- 同步请求全局串行，避免 UI、launchd 和单来源同步重复处理。

### 同步范围

- 首页“立即同步”同步全部 `active` 来源。
- 来源页面“立即同步”只同步当前来源。
- 已存在相同范围同步时，返回现有运行状态。
- 更小范围任务不得绕过全局同步锁并行执行。
- 最近刚完成的立即同步允许使紧随其后的定时扫描跳过重复远端读取。

### 静默时段

- 每小时定时同步保持不变。
- 05:00–11:59 不进行自动发现或自动精修；历史积压仍按每轮上限继续正式处理。
- 12:00 恢复自动发现和自动精修。
- 立即同步和立即精修不受静默时段限制。

## Proposed Approach

保持现有本地单体结构：

```text
launchd / HTML
→ SyncService
  → Source Registry
  → BilibiliAdapter
  → SQLite 状态与来源关系
  → PipelineService
     ├── fast profile
     ├── formal profile
     └── refinement profile
  → ArtifactStore
```

约束：

- 多来源是现有 BilibiliAdapter 和 SyncService 的增量能力，不建立通用多平台 Adapter Registry。
- 后台任务状态持久化到 SQLite。
- Web 只负责启动任务和读取状态。
- SQLite 仍是事实来源。
- 快速版和正式版采用文件版本加 `active_revision` 指针。
- 正式结果必须在完整通过验证后一次性提升，避免原文和摘要版本不匹配。

## Alternatives Considered

### 所有同步都使用正式模型

未选择。立即同步的用户目标是尽快看到内容；只有定时同步和历史积压全部使用正式模型。

### 快速版直接覆盖为正式版

未选择。精修失败可能造成原文和摘要跨版本不一致，也难以恢复。

### 在 UI 中提供快速版／正式版切换

未选择。快速版不需要显示入口，只在当前仍为快速结果时显示状态。

### 多个 B 站账号分别登录

未选择。V1 使用一个小号读取多个公开收藏夹，减少登录和风控复杂度。

### 并发读取多个收藏夹

未选择。串行访问更符合当前个人工具规模和风险控制要求。

### 引入任务队列或 Worker

未选择。SQLite 持久化状态和现有本地进程足以满足 V1。

## Data / API / Tool / Interface Changes

### SQLite

需要从 Schema Version 1 迁移到新版本，至少表达以下职责。

`favorite_sources`：

- 平台和原始 URL。
- 账号 ID 和名称。
- 收藏夹 ID 和名称。
- 来源状态和历史导入策略。
- 最近同步、错误和冷却时间。

`video_source_memberships`：

- `video_id` 和 `source_id`。
- `favorite_time` 和来源内顺序。
- 首次及最后观察时间。
- 移除时间。

现有 `videos` 增加或等价表达：

- `active_revision`。
- `refinement_status`。
- 当前展示排序时间。

现有 `pipeline_stages` 增加或等价表达：

- 处理 Profile：`fast | formal | refinement`。
- reasoning 模式及 effort。
- 精修决策和修改原因。
- 阶段耗时。

现有 `sync_runs` 增加或等价表达：

- 来源范围。
- 当前阶段和当前视频。
- 已扫描、发现、处理和失败数量。
- 历史待处理数量。
- 后台运行状态和经过时间。

### 配置迁移

当前单收藏夹配置必须迁移为一个现有来源，不得要求重新扫码或重新建立 V0 基线。

模型配置从单一 `model` 扩展为：

```text
fast_transcript_model
formal_transcript_model
formal_summary_model
formal_reasoning_effort=max
```

旧 `llm_model` 可作为三个角色的初始迁移值，之后由用户在设置页修改。

### 文件产物

快速版：

```text
transcript.fast.json
transcript.fast.md
summary.fast.json
summary.fast.md
```

正式版：

```text
transcript.refined.json
transcript.refined.md
summary.refined.json
summary.refined.md
```

原始字幕和封面仍保持单份。

V0 现有 `transcript.json`、`summary.json` 和 Markdown 必须在迁移后继续可读，可以被认定为现有正式版本，不强制重新调用模型。

## Error Handling and Recovery

### 来源错误

- URL 格式错误：预览阶段拒绝，不创建来源。
- 收藏夹不存在或不公开：显示明确错误。
- 登录失效：所有来源停止同步并提示重新扫码。
- 单来源不可访问：该来源进入 `unavailable`，其他来源继续。
- 普通新增读取 HTTP 412/429：来源冷却 10 分钟。
- 历史积压读取 HTTP 412/429：来源冷却 20 分钟。
- 来源恢复后保留原有成员关系和成果。

### 模型错误

每个阶段最多尝试三次，沿用：

```text
首次调用
→ 5 分钟后重试
→ 30 分钟后重试
→ needs_review 或 refinement_failed
```

- 快速阶段失败：卡片显示真实错误，不创建虚假快速摘要。
- 正式新视频失败：进入现有 `needs_review`。
- 精修失败：继续显示快速版。
- 模型不存在、API Key 错误、thinking 参数不兼容不得自动换模型。
- 已成功的模型阶段不得因后续阶段失败而重复执行。
- 摘要判断为 `keep` 不视为失败。

### 任务恢复

- 同步任务状态必须写入 SQLite。
- 浏览器刷新或重新打开后能恢复任务进度显示。
- 服务器重启后不得把残留 `running` 永久显示为运行中。
- 中断阶段在下次同步或手动重试时恢复。
- 正式产物写入失败时不得改变 `active_revision`。

## Acceptance Criteria

- 可以通过公开收藏夹 URL 预览账号、收藏夹名称和视频数量。
- 预览不会创建来源、下载字幕或调用模型。
- 可以添加多个公开收藏夹来源。
- 当前 V0 收藏夹和基线可无损迁移为来源。
- 同一视频出现在多个来源时只有一张卡片，并显示多个来源标签。
- 来源暂停后不参加全局同步。
- 首页和来源页面均可立即同步对应范围。
- 历史导入支持“不处理、最新 N 条、全部”。
- 历史积压每轮最多处理 8 条，新收藏优先。
- 历史积压全部直接使用正式模型，不生成快速版。
- 有 `fav_time` 时页面严格按真实收藏时间降序。
- 当前公开测试收藏夹可读取 128 条内容及收藏时间。
- 没有 `fav_time` 时使用来源顺序和观察时间回退。
- 立即同步中新视频正常使用快速字幕模型和正式摘要模型。
- 快速结果卡片显示“快速版”。
- 定时发现的新视频直接生成正式版且不显示版本标签。
- 快速版精修正常最多新增两次模型调用。
- 精修模型可决定保留或修改原快速摘要。
- 精修成功后页面完全不显示快速／精修版本信息。
- 精修失败三次后仍能阅读快速内容并手动重试。
- 快速和正式文件分别保留，UI 不提供快速历史入口。
- 设置页显式显示 `max`，不显示 `xhigh`。
- 三个模型角色可以分别测试。
- 不可用模型不得静默回退。
- 立即同步返回后台运行状态，浏览器刷新不丢失进度。
- 重复点击不会启动重复同步。
- B 站来源、分页、视频和字幕请求保持串行。
- 定时启动抖动为 60–300 秒，立即同步无启动抖动。
- 普通新增的 412/429 冷却 10 分钟，历史积压冷却 20 分钟。
- 05:00–11:59 不自动扫描或精修，但历史积压 24 小时可处理；手动操作仍可执行。
- V0 已有视频、忽略状态、原文、摘要和本地文件升级后保持可用。
- 现有 V0 测试继续通过，新增 V1 测试通过。
- 实现不包含 Non-goals 中明确排除的能力。

## Risks

- B 站非官方接口可能改变字段、权限和风控行为。
- 公共收藏夹可能临时转为私密或删除。
- 多来源下同一视频的移除与重新加入关系比 V0 更复杂。
- DeepSeek 或其他兼容服务对 thinking 参数的实现可能不同。
- `max` 推理可能明显超过当前 120 秒超时。
- 后台同步若仍与 Web 进程共享生命周期，服务器退出会中断当前任务。
- Schema 迁移错误可能影响现有 V0 数据。
- 历史全部导入可能产生长时间 B 站读取和大量模型调用。
- 公开收藏夹的 `fav_time` 是否长期稳定属于外部接口风险。

## Assumptions

- 用户在设置页填写实际可用的模型 ID；规格不硬编码特定 DeepSeek 模型 ID。
- 现有 V0 `transcript.*` 和 `summary.*` 在迁移中认定为正式版本。
- 关闭浏览器仅指关闭或刷新页面，不代表退出拾流服务器进程。

## Stop and Escalation Conditions

后续实现遇到以下情况必须停止并请求确认：

- 无法在不丢失现有 V0 数据的情况下完成 Schema migration。
- 公开收藏夹读取必须修改上游 CLI 或引入另一个 B 站 SDK。
- DeepSeek 的真实 API 无法通过 OpenAI-compatible 请求表达 thinking 或 `max`。
- 后台同步必须引入独立 Worker、消息队列或常驻服务。
- 多来源要求改变视频唯一身份或为同一 BV 重复生成内容。
- 需要增加 B 站写操作或多套账号凭据。
- 必须读取视频简介中的外部链接。
- 真实收藏时间无法继续取得，且需要改变已批准的排序语义。
- 任何 Acceptance Criterion 无法满足。
- 实际复杂度明显超过 Complexity Budget。
- 继续工作需要实现 Non-goals 中的能力或形成通用框架。
